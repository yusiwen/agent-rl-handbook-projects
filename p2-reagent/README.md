# P2 - process feedback and turn-level credit

**Status: built and run end to end, and the one join it was missing now exists in Project 3.** The table policy proves the credit
machinery offline; a LoRA fine-tune on the oracle's own trajectories took the solve rate from 2/43 to
30/43 (greedy) and 8/129 to 91/129 (sampled) at 100% format compliance; the served loop ran 387
episodes over HTTP; an 8B judge scored real trajectories and disagreed with the rule often enough to
be demoted from reward to diagnostic; and a token-level objective whose adapter updates in the same
process where it generates moved six calibrated tasks from 42/60 to 60/60. **The join between the
last two is now built in [`../p3-verl`](../p3-verl):** served sampling over HTTP, the gradient in the
training process, and the result registered as the next round's adapter in 12-13 ms. At ten samples
per task one update took six calibrated tasks from 18/60 to 60/60; at five samples the same loop
plateaued at 25/30, which turned out to be the budget's ceiling rather than a task's wall - a task
whose whole group fails contributes no gradient, so it is never trained on. This project's own served
check stays read-only.
Written with Chapter 6.

The design document Chapter 6 asks for is [`DESIGN.md`](DESIGN.md): the task as an MDP, the signal
level chosen for each kind of decision with the reason the level below was not chosen, which of the
four difficulties this task actually has (sparse feedback and structural label noise, not length),
and the loss mask with the failure a wrong one produces.

## What you build

A multi-turn agent loop with a critic in it, and credit that can be attributed to a turn rather
than to an episode:

```
task -> agent loop (finite action menu per turn) -> per-turn signals + critic verdicts
          |                                             |
          |                                             +-- trace, critique, score (three outputs)
          +-- turn boundaries recorded, mask built from the roles
                                    |
                          fusion point (weights written down)
                                    |
                     group-relative advantage -> policy update
                                    |
                    round N+1 samples from the policy round N produced
```

## The nine faces

**1. Problem.** A trajectory-level reward tells you an attempt failed, not which turn did it; this
project builds the plumbing that makes a per-turn signal usable, and measures whether the signal
reaches the next round of sampling.

**2. Environment.** Pure Python standard library, no container, no GPU, no network. Two simulated
families (`files`, `ledger`) with a reset between attempts and a finite action menu per turn. The
"environment version" analogue of a container digest is `env.ENV_VERSION` plus each family's own
version, and it travels in every row.

**3. Data.** No dataset: the tasks are 43 programmatic problems in two families (`files`, `ledger`)
whose goals are checkable, and
the attempts are generated by the policy that is being trained. The point is the *signal*, so the
data is deliberately small enough that a table can learn it in six rounds.

**4. Architecture.** `env.py` (families, menus, progress) - `agent.py` (sampling, turn recording,
mask) - `critics.py` (rule, scripted, model, budget) - `fusion_policy.py` (one function, weights and
conflict policy beside it) - `train.py` (advantages, turn weights) - `loop.py` (round, checks,
record). The policy is `policy.py`: a softmax table, so the gradient is closed-form and the entropy
is a number you can watch.

**5. Config.** Defaults that matter: `--samples 8` (the GRPO group), `--rounds 6`, learning rate
0.3, sampling temperature 1.0, `max_turns` 6, `credit=trajectory`. Weights: rule-only
`{outcome 0.6, turn 0.4}`, full `{outcome 0.5, turn 0.3, critic 0.2}`. A six-round run on three
tasks x eight samples is **under a second** of compute - the expensive part of this project is the
served judge, not the loop.

**6. Source.** The three breakpoints Chapter 6 names: the **advantage** (`train.group_advantages`),
the **fusion point** (`fusion_policy.fuse_terms`, which returns contributions and conflicts), and
the **turn boundaries** (`common.mask.turn_boundaries`, checked against every row by
`common.checks.check_boundaries`).

**7. Runs.** `runs/<run-id>/` with a header (env version, config digest, code sha, project) and one
`round-NNN.jsonl` per round. Every row carries `extras.policy_version`: the version that *sampled*
it. The RL stage writes the same shape through `env/rl_step.py`, so its tables can be re-derived
instead of trusted: `p2-rl-step` (step A), `p2-rl-step-2` (step C) and `p2-rl-eval` /
`p2-rl-eval-2` (held out, both adapters).

```
python3 p2-reagent/checks/run_p2_loop.py --rounds 6 --samples 8
python3 p2-reagent/checks/run_p2_loop.py --stage full --critic fixture \
    --fixtures p2-reagent/fixtures/critic.jsonl
```

**8. Failure modes.** Four, all found by running the thing rather than by reading it - see below.

**9. Evaluation.** `p2-reagent/checks/check_p2.py` (in the gate): every task solvable from its own
menu, the common five checks pass, the same sample ids reappear with changed rewards, the policy
version advances with a changed parameter digest, no entropy cliff, every judge call has a gate
decision, and at least one rule-vs-critic conflict is found and logged.

`checks/measure_policy.py` is the tool behind the fine-tune numbers: it runs a served model as the
policy over the same task set, one sample per task for the greedy figure and several for the sampled
one, so `2/43 -> 30/43` and `8/129 -> 91/129` can be reproduced rather than taken on faith.

## The four bugs this project found by being run

Each one is pinned by a test, because each is the kind of thing that is invisible in a reward curve:

1. **An activity-based turn score teaches a policy to be busy.** With `ok` scored 0.8 because the
   state changed, the demo policy learned to repeat a harmless action until the turn cap stopped it
   - Chapter 6, Lesson 4's Echo Trap, reproduced accidentally. The turn score is now the *delta* in
   distance to the goal.
2. **A mean over turns lets padding beat acting.** Two neutral turns plus a wrong report averaged
   higher than the right action plus a wrong report, so the policy padded. The fused turn term is
   now the *maximum* progress reached.
3. **A distance-to-goal score rewarded the distractor.** In the ledger task, `add 5` landed nearer
   to 7 than the correct `add 12` did. Progress now follows the required sequence.
4. **A menu that omits the correct action makes a task impossible.** The `files` family shared one
   menu, so the delete task's `rm tmp.log` was never offered; the loop "failed to learn" an
   environment bug. Menus are now generated per task, and the gate asserts each task is solvable.

## What is not here yet

  here is a one-argument change, deferred so the mechanism is documented in one place.
  Everything in Chapter 6's stage list now runs: SFT (`env/sft.py`), the served loop
  (`served_policy.py` + `checks/run_p2_served.py`), and the judge (`ModelCritic` against a real 8B
  model - which is why it was demoted out of the reward).
- **Multi-GPU and a real task distribution.** Six calibrated tasks with ten samples each is a
  demonstration, not a training set. The held-out check shows one family's procedure transferring and
  a sibling operation regressing, which is what one round on six tasks buys.
- **ALFWorld / tau-bench**: `env.py` is the seam. Replacing it does not touch the critics, the
  fusion, the advantages or the loop.

## The format baseline, measured before the fine-tune

`python3 p2-reagent/checks/measure_format.py --base-url http://192.168.2.40:8000 --model qwen3-1.7b`,
2026-10-18, all 43 tasks, first turn only, the same prompt and the same parser the loop uses:

| temperature | replies with a usable `ACTION` line |
| --- | --- |
| 0.0 | 43/43 (100%) |
| 1.0 | 43/43 (100%) |

The result changes what the fine-tune is for. The plan going in was "fine-tune until format
compliance reaches 90%"; the checkpoint is already at 100% on this prompt, so there is nothing to
reach. The prompt is why: it names a mechanical slot (`ACTION: <action>`) and prints the menu one
entry per line to copy from. Chapter 7 measured the same lever from the other side - naming the
slot took answer declarations from 26% to 88%, while a style instruction ("end with the number
alone on the last line") did not - and this is that finding applied rather than re-learned.

So the fine-tune's target is the task, not the syntax. The action space is two to three steps deep
over a nine-entry menu, and at a cold uniform policy 18 of 43 groups show any reward variation at
all; the rest are flat because no sample in the group got both steps right. Format compliance stays
in the loop as a guard rail: if it drops below the baseline the fine-tune broke the interface, and
that is a regression whatever it did to the score.

## What the fine-tune changed, measured

Two readings, 2026-10-18, all 43 tasks, the same prompt and parser throughout. The base checkpoint
and the fine-tuned one are both served, so the comparison is two endpoints rather than two claims.

| policy | solved, greedy | solved, 3 samples at T=1.0 | usable turns | mean turns |
| --- | --- | --- | --- | --- |
| `Qwen/Qwen3-1.7B` | 2/43 (5%) | 8/129 (6%) | 100% | 5.53 |
| after P2-prime | **30/43 (70%)** | **91/129 (71%)** | 99-100% | 3.47 |

Format compliance was already 100% before training, so this number is not about syntax: the same
contract, answered correctly twelve times as often. The demonstration set is the oracle's own
trajectories - 117 turns over 43 tasks - and the loss covers the reply only.

### The three ways it still fails

Thirteen tasks fail consistently, and they fail in three different ways, which matters for what
the next stage should and should not try to fix:

- **Miscounting.** `files-r02`: the move is right (`mv final.csv final.log`) and the report is
  wrong (`done 2`). The policy can act and cannot count, which is a reasoning limit, not a format
  one.
- **Not terminating.** `files-rename-count`: the move is right, then `ls`, `cat final.txt`,
  `cat draft.txt`, `ls` until the turn budget runs out. It keeps verifying instead of reporting.
- **Order.** `ledger-03`: both moves are taken, in the wrong order, so the balance is right and the
  plan is not. The environment requires the order the task states, deliberately: a sequence task
  whose order does not matter is a sum, and a sum is a different lesson.

None of the three is a format problem, and none is fixed by more demonstrations of the same shape.
They are the honest ceiling of this fine-tune, and the reason the loop stage has something to
measure rather than a saturated pass rate.

2026-10-18, `code_sha git:75edcf1`, 3 rounds x 3 samples x 43 tasks, record in
`runs/p2-loop-rule-only-turn-6`.

| round | solved | mean reward | usable `ACTION` lines |
| --- | --- | --- | --- |
| 0 | 94/129 (73%) | +0.811 | 1330/1336 (99.6%) |
| 1 | 89/129 (69%) | +0.783 | |
| 2 | 97/129 (75%) | +0.822 | |

1,336 model calls in 189 s. The spread across rounds is sampling noise at temperature 1.0 - about
five points either way on 129 episodes - and not learning: a served policy has no update, which is
why `Config.served` drops the lineage and entropy checks instead of letting them fail for a reason
that is the experiment's design.

### The finding: a good policy makes groups flat too

Re-running the shared checks over the recorded rollouts, offline: mask, boundaries and terms pass;
round stability passes, with 11 and 12 of 129 shared samples changing reward between rounds;
**advantage spread fails at 6-8 of 43 usable groups (14-19%)** - lower than the 18/43 the cold
policy produced.

The reason is the mirror image of the cold-start problem. With 72% of episodes solved, most groups
are three-for-three and contribute a zero advantage; a cold policy contributes zeros because no
sample succeeds, a competent one because they all do. Both ends are flat and the gradient lives
only in the band between them - Chapter 7's "in-band difficulty" seen from the policy side rather
than the task side.

That is a task-difficulty finding, not a loop defect, and it sets the agenda for the next stage:
calibrate the tasks to where this policy is right about half the time, rather than adding more
tasks it almost always solves.

One correction, kept because it is instructive. The record above comes from `git:75edcf1`, and its
output still contains a **lineage failure**: "the parameters are unchanged from round 0, so the
update did nothing". The guard that drops lineage and entropy for a served policy had been added in
`run_round`, but the loop still ran both checks at its own level, so the failure survived. It is
fixed - the guard now sits where the checks are attached - and the run's data is unaffected, because
what was wrong was the verdict on it, not the rollouts. A frozen policy cannot fail "the update
changed the parameters"; it can only be asked it by mistake.

## Calibration: which tasks the loop can learn from

`python3 p2-reagent/checks/calibrate_tasks.py --run runs/p2-loop-rule-only-turn-6` reads the
recorded attempts and writes `fixtures/calibration.json`. Pointing the same loop at different
subsets changes the one number that matters, and nothing else:

| subset | tasks | groups with a non-zero advantage |
| --- | --- | --- |
| every task | 43 | 14-19% |
| solved share between 11% and 89% | 11 | 36-45% |
| solved share between 1/3 and 2/3 | 4 | **100%** |

The middle row is the instructive one: a task solved 11% of the time still looks flat to a group of
five, because five samples of an 11% event usually fail together. What the group needs is a per-
*sample* success rate near one half, and the per-task rate one measured is that number only when
there are enough samples to resolve it - which is why the band is read from data with a stated
number of attempts, not guessed.

The four tasks are `files-r03`, `files-r06`, `files-r07` and `files-r09`. The bottom row is 2 rounds
x 5 samples x 4 tasks at `code_sha git:7ced1af`: 176 calls, 24 s, spread 100% in both rounds.
Nothing about the loop changed between the rows - only which tasks it was pointed at.

## The judge, measured rather than assumed

`python3 p2-reagent/checks/run_p2_fusion.py`, 2026-10-18, on the five-task calibrated band
(`fixtures/calibration-wide.json`), budget `[0.5, 0.9]`, record `runs/p2-loop-full-turn-2`.

| judge | holds the format on a six-turn trace | episodes judged | rule-vs-judge conflicts |
| --- | --- | --- | --- |
| `Qwen/Qwen3-1.7B` (the base checkpoint) | no - stops after about four turns and raises | 0 | - |
| `nvidia/Qwen3-8B-NVFP4` | yes, 35 of 35 | 35 of 50 | **106** |

The budget behaved as designed: 35 episodes were judged, 15 were skipped, and every skip names the
rule score it decided on.

The verdict on the judge is the conflict count, and it is bad. 106 disagreements across 35 judged
episodes is about three per episode - roughly three quarters of all judged turns scored at least
0.25 apart. What rules out averaging them away is that the disagreements are systematic:

```
turn 1: rule=0.50 vs model=0.00  (changed nothing that matters / it only listed files)
turn 2: rule=0.50 vs model=0.00  (changed nothing that matters / it only viewed a file)
```

The rule critic treats reading as a neutral turn - it taught nothing, it was not a failure - because
an earlier version that scored activity taught the policy to repeat a harmless action until the turn
cap (the Echo Trap, Chapter 6). The judge treats reading as a failure. Fusing the two as a dense
reward would teach the policy not to look before it acts, the opposite of what the demonstrations
were built for.

So the judge stays, and stays out of the reward. It is a diagnostic: it says in words which turns a
second model thought were wasted. The dense signal remains the rule's progress delta. The plan set
50% as the conflict rate above which the judge would be demoted; the measurement is above 75%, and
the conclusion is not "tune the weights" but "this is not a reward".

## Where this stage ends

Four stages are built and measured - fine-tune, served loop, calibration, judge - with their numbers
above and their records in `runs/`. The update on top of the served policy is built in
[`../p3-verl`](../p3-verl) and measured there (11/30 to 25/30 in one update, 12-13 ms per sync); what
this stage still does is run the served loop frozen, which is why its own rounds are flat and why
`Config.served` drops the checks that assume training.

Doing that update means putting the fine-tuned weights back into a training loop - an on-policy or
off-policy group-relative step against the served checkpoint - which is Project 3's subject and
Chapter 9's machinery. What this stage delivered is the measurement of *whether* the credit signal
is worth training on, and the answer so far is: the machinery is sound, the tasks have to be
calibrated per sample, and a 1.7B rule-plus-judge reward is not yet a reward.
